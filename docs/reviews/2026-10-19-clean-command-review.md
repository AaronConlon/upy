# clean 命令逻辑审核

- 审核日期：2026-10-19
- 审核对象：当前工作区中的 `clean` 命令实现（包含尚未提交的代码）
- 审核范围：`internal/commands/clean.go`、`internal/cleaner/cleaner.go` 及其测试；同时核对部署流程、状态读写、项目登记和交互选择逻辑。
- 审核方式：静态代码分析及现有测试。下述触发场景根据代码路径推导，未完成独立动态复现。

## 审核结论

共发现 5 项逻辑问题：3 项 P1、2 项 P2。主要风险是活跃版本保护不足，以及部署和清理之间缺少互斥；其次是删除失败仍报告成功、批量操作忽略指定范围。

| 编号 | 优先级 | 问题 |
| --- | --- | --- |
| CLEAN-001 | P1 | 状态与 current 不一致时，可能删除正在使用的版本 |
| CLEAN-002 | P1 | 无法识别活跃版本时，仍将全部 release 作为删除目标 |
| CLEAN-003 | P1 | 并发清理可能删除正在部署的临时目录或新版本 |
| CLEAN-004 | P2 | 删除错误被吞掉，可能虚报成功并继续注销项目 |
| CLEAN-005 | P2 | 批量选择忽略显式参数，扩大清理范围 |

## CLEAN-001：状态与 current 不一致时误删活跃版本

**位置**：`internal/cleaner/cleaner.go:44–49`，`AnalyzeProject`。

只要 `state.json` 存在非空 `currentVersion`，实现就直接使用它，不再检查 `current` 的实际指向。部署流程会先激活版本、切换 `current`，再通过 `state.WriteAtomic` 更新状态，因此两个来源可能不一致。

**触发场景**：

1. 状态记载当前版本为 `v1`。
2. 部署切换 `current` 到 `releases/v2/dist`。
3. 写入状态失败，状态仍为 `v1`。
4. 执行 `clean --old-releases` 或 `clean --all`。

清理仅保护 `v1`，将实际提供服务的 `v2` 作为旧版本删除，导致 `current` 失效。

**建议**：分别解析状态和软链，在一致性恢复前保护两个来源指向的版本；或者发现冲突后停止版本清理并返回明确错误。软链解析应基于规范化后的路径与项目 `releases` 目录关系，避免仅使用字符串截取。

**建议验证**：构造状态为 `v1`、软链指向 `v2` 的目录，断言清理不会删除软链实际指向的版本。

## CLEAN-002：未知活跃版本时删除全部 release

**位置**：`internal/cleaner/cleaner.go:83–87`，`AnalyzeProject`。

当状态读取失败、状态没有版本，且软链解析也失败时，`CurrentVersion` 为空。当前判断仅在版本非空且目录名相等时跳过，因此其余普通版本目录全部进入 `OldReleases`。

**触发条件**：状态丢失或损坏，并且 `current` 缺失、不可读取或无法按当前规则解析。此时无法证明任何目录已经过期，但常规清理仍会删除全部版本。

**影响**：丢失部署产物；若运行中的 Docker 服务仍依赖这些目录，还可能影响服务运行或后续恢复。

**建议**：存在版本目录但无法确定活跃版本时，停止版本清理并返回错误。Bundle 缓存是否继续清理可单独处理；删除所有版本应由明确的 `--purge` 操作承担。

**建议验证**：覆盖缺失状态、损坏状态、缺失软链及无法解析软链等组合，断言普通清理不会在版本未知时删除全部 release。

## CLEAN-003：并发清理破坏正在进行的部署

**位置**：`internal/cleaner/cleaner.go:160–166`，`CleanTmpDeployDirs`；以及 `CleanOldReleases` 的扫描、删除流程。

临时目录清理仅依据 `.tmp-deploy-` 前缀判断是否可删除。部署流程通过 `os.MkdirTemp(releasesDir, ".tmp-deploy-")` 创建正在使用的解压目录，同样满足该条件。当前清理和部署之间没有共用项目锁。

**触发场景**：部署正在解压 Bundle 时，另一进程执行 `clean --all` 或 `clean --old-releases`，删除正在使用的临时目录，导致部署失败。新版本移动到正式 release 目录后、状态更新前，清理也可能将其作为旧版本删除。

**建议**：部署与清理使用同一个项目级跨进程锁，并覆盖目标扫描至删除完成的整个过程。仅根据目录前缀或年龄不足以可靠证明目录已不再使用。

**建议验证**：使用同步点暂停部署，在解压阶段及正式版本安装后分别启动清理，验证清理会等待或明确拒绝，不会删除正在部署的目录。

## CLEAN-004：删除失败仍报告成功

**位置**：

- `internal/cleaner/cleaner.go:114–121`：`CleanBundles` 忽略文件信息读取和删除错误。
- `internal/cleaner/cleaner.go:138–144`：`CleanOldReleases` 忽略目录删除错误。
- `internal/cleaner/cleaner.go:166–171`：`CleanTmpDeployDirs` 忽略目录删除错误。
- `internal/cleaner/cleaner.go:183–208`：`PurgeProject` 忽略删除错误，在删除前累计释放空间。
- `internal/commands/clean.go:350–383`：常规瘦身即使部分步骤失败，仍返回成功。
- `internal/commands/clean.go:441`：清空后忽略注销错误。
- `internal/commands/clean.go:458–460`：批量清理忽略各项清理错误。

**触发条件**：权限不足、文件系统只读或其他删除失败。

**影响**：文件仍然存在，但命令返回成功，自动化无法通过退出状态识别失败。`PurgeProject` 还可能虚报释放空间；调用方随后继续注销项目，使仍有部署产物的项目从登记列表消失。

**建议**：收集并返回扫描与删除错误，成功和失败分别汇报；只对确认成功的删除累计释放空间。Purge 未完整成功时不应按完整成功流程注销；注销失败也应明确报告。

**建议验证**：使用可控的权限限制或文件系统故障注入，验证部分失败会返回非空错误、释放空间不会包含失败项，且不会错误注销项目。权限测试需考虑高权限账户可能绕过权限限制。

## CLEAN-005：批量清理忽略指定参数

**位置**：`internal/commands/clean.go:446–469`，`cleanAllProjects`。

批量分支只使用 `args.Yes`，固定依次执行 Bundle、旧版本和临时目录清理，没有遵循 `Bundles`、`OldReleases`、`Unregister` 或 `Purge` 参数。

**触发场景**：有多个可选项目时执行 `clean --bundles`，随后选择“全部已登记项目”。实际操作会额外删除旧版本和临时目录。传入 `--unregister` 后选择该选项，也会变成常规瘦身，无法完成注销。

虽然菜单将批量选项描述为“常规瘦身”，但它与显式参数产生冲突，命令没有校验或解释这一覆盖行为。

**建议**：批量执行复用单项目的参数分派逻辑；若批量仅支持常规瘦身，应在冲突参数存在时隐藏该选项或返回明确错误，避免静默扩大删除范围。

**建议验证**：覆盖多项目场景下各参数与批量选项的组合，重点断言 `--bundles` 不会删除 release，以及 `--unregister` 不会删除任何物理文件。
